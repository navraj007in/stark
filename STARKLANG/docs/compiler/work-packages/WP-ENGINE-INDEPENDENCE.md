## 0. Governing Claim

> **Every semantic authority shared by two or more execution engines is enumerated, and each has a non-differential check against an external authority or a registered residual.**

A valid external authority may be:

- a normative STARK specification rule;
- an independently authored positive/negative conformance pair;
- a proof-like invariant test;
- a mutation killed by an independently derived test;
- an external semantic oracle;
- a platform or ABI contract;
- a registered Compiler Decision with executable controls.

Tests whose expected results are generated by the shared authority under test do not qualify as independent evidence.

---

## 1. Problem Statement

STARK’s differential-testing strength comes from agreement across three execution paths:

```text
HIR interpreter
MIR interpreter
native backend
```

The confidence value of that agreement depends on implementation independence.

At the same time, the single-authority programme has deliberately centralised semantic rules to prevent drift:

- RB0;
- DEV-128;
- `mir_ty_is_copy`;
- shared trait-contract tables;
- `check_condition`;
- canonical type conversion;
- provider metadata;
- shared ownership and representation predicates;
- “one rule, one owner” repairs.

These centralisations were individually justified, but each can convert a divergence risk into a shared-fate risk.

A defect in a shared authority may produce agreement across all engines and remain invisible to differential testing.

DEV-118 demonstrates the class:

> The `Hash + Eq` omission existed across all three engines, so agreement could not reveal it.

The required audit is therefore not another general correctness review. It must determine:

```text
which semantic facts are independently implemented
which semantic facts are shared
which engine paths inherit common earlier decisions
which shared facts have independent specification evidence
which shared facts remain blind spots
```

---

## 2. Scope

### Included

1. Semantic functions, predicates, tables, schemas, and normalization rules consulted by two or more engines.
2. Shared earlier pipeline stages whose output constrains multiple later engines.
3. Provider and host-resource machinery shared by MIR and native execution.
4. Test-oracle and fixture generation paths shared across engine evidence.
5. Native backend assumptions delegated to Rust and rustc.
6. Explicit role and risk profile for each engine.
7. Mutation recommendations for shared authorities.
8. Release-language implications.

### Excluded

- general compiler quality review;
- full source-code correctness audit;
- performance-only utilities;
- formatting and diagnostic wording unless semantically load-bearing;
- archived engines or abandoned backends;
- speculative future backends;
- repairs to findings, except trivial documentation corrections;
- platform-roadmap scheduling or release-gate changes.

Findings become DEV candidates, owner decision requests, AS8 inputs, scoped follow-up work
packages, or registered residuals.

## 3. Engine Model

This packet must not assume the three engines are equivalent.

### 3.1 HIR interpreter

**Role**

- source-shaped execution path;
- rapid frontend semantic vote;
- useful for checker/interpreter agreement;
- remains the semantic reference under `COMPILER-CHARTER.md` §1.6 rule 6 until an explicit later
  gate changes that decision;
- reference status does not make its implementation infallible, so representation and execution
  seams still require independent specification-derived controls.

**Known risk profile**

- weakest-typed execution path;
- hand-maintained value representation;
- method-return and representation seams;
- historically defect-rich in recent DEV classes;
- may accept behavior native lowering cannot represent.

### 3.2 MIR interpreter

**Role**

- executes verified MIR;
- tests semantics after lowering;
- separates frontend intent from native code generation;
- validates the admitted IR model.

**Known risk profile**

- inherits lowering defects;
- may share representation and type predicates with native;
- recent quietness may indicate strength or under-exercise;
- agreement with native is not fully independent where both consume the same MIR.

### 3.3 Native backend

**Role**

- production execution path;
- provider integration;
- resource lifecycle;
- platform behavior;
- ABI and representation realization.

**Known risk profile**

- inherits frontend and MIR lowering decisions;
- delegates substantial enforcement to Rust and rustc;
- owns native representation, drop, FFI, and platform risks;
- sensitive to toolchain identity and emitted-Rust assumptions.

### 3.4 rustc and Rust

Rustc is not a fourth equivalent STARK semantic oracle. It is part of the native trusted execution base:

```text
STARK source
→ STARK checking and lowering
→ emitted safe Rust
→ rustc validation and compilation
→ native execution
```

The packet must identify semantic assumptions delegated to Rust/rustc and record the toolchain identity required to reproduce native artifacts.

## 5. Execution packets

### EI0 — Freeze vocabulary and audit method

#### Objective

Define classifications before examining results.

#### 0.1 Dependency classification

```text
DIRECT
INDIRECT
NONE
UNKNOWN
```

- **DIRECT:** the engine calls or reads the authority directly.
- **INDIRECT:** the engine consumes IR, metadata, normalized types, or generated structures produced by the authority.
- **NONE:** no relevant dependency found.
- **UNKNOWN:** insufficient evidence; resolve or register as a residual.

#### 0.2 Differential visibility

```text
VISIBLE
PARTIALLY_VISIBLE
INVISIBLE
UNKNOWN
```

- **VISIBLE:** a defect should affect one engine independently and create disagreement.
- **PARTIALLY_VISIBLE:** some defect classes diverge while others are inherited.
- **INVISIBLE:** relevant engines inherit the same authority or output.
- **UNKNOWN:** visibility has not been established.

#### 0.3 Evidence independence

```text
SPEC_DERIVED
EXTERNALLY_DERIVED
HAND_AUTHORED
CROSS_ENGINE_DERIVED
IMPLEMENTATION_GENERATED
SHARED_FIXTURE_GENERATOR
UNKNOWN
```

`SPEC_DERIVED`, `EXTERNALLY_DERIVED`, and independently `HAND_AUTHORED` evidence are strongest.

`CROSS_ENGINE_DERIVED`, `IMPLEMENTATION_GENERATED`, and `SHARED_FIXTURE_GENERATOR` are correlated unless an independent control exists.

#### 0.4 Authority category

```text
SHARED_PREDICATE
SHARED_TYPE_TABLE
SHARED_NORMALIZATION
SHARED_LOWERING
SHARED_IR
SHARED_PROVIDER_SCHEMA
SHARED_ABI_MAPPING
SHARED_ERROR_MAPPING
SHARED_TEST_ORACLE
RUSTC_ASSUMPTION
ENGINE_LOCAL
```

#### Acceptance criteria

- classifications are frozen;
- `UNKNOWN` is not silently treated as independent;
- direct and indirect dependencies are distinguished;
- evidence-source correlation is included.

### EI1 — Build the shared-fate register

#### Objective

Enumerate semantic authorities shared by two or more engines.

#### Search strategy

Start from known single-authority work:

```text
RB0
DEV-128
mir_ty_is_copy
trait contract table
check_condition
copy eligibility
drop eligibility
type normalization
provider signatures
HostResource mappings
error and trap categories
numeric conversion rules
reference weakening and reborrowing
unit canonicalization
generic compatibility
iterator item representation
```

Also inspect shared semantic data:

- enums;
- lookup tables;
- maps;
- manifests;
- provider declarations;
- ABI metadata;
- canonical type conversion;
- status-code mappings;
- generated MIR conventions;
- target-layout assumptions.

Do not limit the audit to shared functions.

#### Required register columns

| Field | Required content |
|---|---|
| Authority ID | Stable identifier |
| Semantic fact | Rule or behavior decided |
| Category | Frozen authority category |
| Implementation owner | Function, table, module, or schema |
| HIR dependency | Direct, indirect, none, unknown |
| MIR interpreter dependency | Direct, indirect, none, unknown |
| Native dependency | Direct, indirect, none, unknown |
| rustc dependency | Relevant assumption or none |
| Differential visibility | Visible, partial, invisible, unknown |
| Evidence independence | Frozen evidence classification |
| Independent evidence | Exact spec/test/CD/mutation reference |
| Residual | Missing evidence or limitation |
| Risk | Low, medium, high, critical |
| Owner | Responsible work package or maintainer |
| Review trigger | Change that reopens the row |

#### Machine-readable register

Publish the human-readable register at
`STARKLANG/docs/compiler/ENGINE-SHARED-FATE-REGISTER.md` using the columns above, and create the
equivalent machine-readable `STARKLANG/docs/compiler/engine-shared-fate.json`.

Suggested shape:

```json
{
  "schema_version": 1,
  "revision": "<git-sha>",
  "authorities": [
    {
      "authority_id": "ESF-COPY-001",
      "semantic_fact": "Whether a MIR type is structurally Copy",
      "category": "SHARED_PREDICATE",
      "implementation_owner": "starkc/src/mir/...",
      "dependencies": {
        "hir": "INDIRECT",
        "mir_interpreter": "DIRECT",
        "native": "DIRECT",
        "rustc": "NONE"
      },
      "differential_visibility": "PARTIALLY_VISIBLE",
      "evidence_independence": "SPEC_DERIVED",
      "independent_evidence": [
        "OWN-COPY-001",
        "copy_canon_matrix",
        "mutation-batch-reference"
      ],
      "residual": null,
      "risk": "HIGH",
      "responsible_owner": "WP-C7.8-RB0",
      "review_trigger": "Copy predicate or representation changes"
    }
  ]
}
```

#### Acceptance criteria

- every known shared semantic authority has a row;
- indirect shared fate through MIR or normalized types is represented;
- shared data tables are included;
- empty evidence columns become residuals;
- no material authority remains `UNKNOWN` without an owner.

### EI2 — Audit evidence independence

#### Objective

Determine whether engine agreement and conformance evidence rely on correlated or self-generated oracles.

#### Required targets

Inspect:

- differential expected-value generation;
- snapshot generation and refresh process;
- frozen corpus provenance;
- shared fixture parsers;
- test helper tables;
- expected diagnostics generated from implementation constants;
- HIR output reused as MIR/native expected output;
- package consumers shared across multiple claims;
- generated tests based on the same semantic authority under test.

#### Required questions

1. Who or what generated the expectation?
2. Does the expectation depend on the implementation being tested?
3. Is the same fixture parser or semantic table used by multiple engines?
4. Would the evidence detect a shared-authority defect?
5. Is there a negative control?
6. Is there an independent spec-derived assertion?

#### Output

Create `STARKLANG/docs/compiler/ENGINE-EVIDENCE-INDEPENDENCE.md` with:

| Evidence ID | Engines covered | Expectation source | Independence | Shared-fate risk | Independent control | Residual |
|---|---|---|---|---|---|---|

#### Acceptance criteria

- implementation-generated expectations are identified;
- correlated fixture generators are identified;
- snapshot refresh risk is documented;
- evidence unable to detect shared-fate defects is not described as independent;
- each high-risk evidence source has a control or residual.

#### Objective

Make the native trusted base and toolchain assumptions explicit.

#### Required assumption classes

Inspect and record assumptions concerning:

- argument evaluation order;
- borrow activation and aliasing;
- generated-reference validity;
- drop order;
- temporary lifetime;
- pattern-matching behavior;
- integer overflow configuration;
- panic strategy;
- unwinding behavior;
- FFI calling conventions;
- ABI integer widths;
- layout and representation;
- enum and option lowering;
- safe Rust rejection as a backend validity check;
- edition behavior;
- compiler-version-specific acceptance;
- target-specific behavior.

DEV-150 must be included:

```text
HIR accepted
MIR/native lowering emitted Rust
rustc rejected generated Rust
```

```text
Rust toolchain channel/version

Cargo version
target triple
host triple
panic strategy
backend/runtime versions
provider versions
build profile
```

#### Acceptance criteria

### EI5 — Mutation target calibration

#### Objective

Use the register to select and prioritise AS8 mutation trials.

#### Mutation tags

```text
SHARED_AUTHORITY
ENGINE_LOCAL
BACKEND_ASSUMPTION
EVIDENCE_SHARED
```

#### Priority rule

Prioritize:

1. high-risk invisible shared authorities;
2. shared type and representation predicates;
3. generic compatibility and trait tables;
4. provider and resource mappings;
5. canonicalization helpers;
6. error-category mappings;
7. rustc-sensitive lowering decisions;
8. correlated evidence generators.

#### Required outputs

For each high-risk row add:

```text
recommended mutation batch
selected tests
expected independent control
survivor consequence
```

A killed shared-authority mutation is not automatically sufficient. Confirm that the killing test is independently derived rather than generated from the same authority.

#### Acceptance criteria

- AS8 receives a ranked target list;
- high-risk shared authorities enter bounded mutation batches;
- kill rates are reported separately by mutation tag;
- shared-authority survivors become immediate AS8 residuals or DEV candidates.

### EI6 — Public claim calibration

#### Objective

Produce release language that accurately reflects engine independence.

#### Prohibited unqualified claim

Do not use:

> “STARK has three independent implementations of its semantics.”

unless the register supports it and limitations are published.

#### Preferred release language

> STARK uses three execution paths with deliberately different roles. Some semantic authorities are shared to prevent implementation drift; those shared authorities are separately checked through specification-derived conformance tests, mutation testing, executable gates, and registered residuals.

A stronger claim may be used only if earned.

#### Acceptance criteria

- public language matches measured independence;
- rustc’s role is accurately described;
- shared-fate residuals are not concealed;
- C10 and public announcement copy consume the approved wording.

This sequence is a planning aid, not a duration estimate. AS0 reports the actual inventory size

### Packet A — vocabulary and initial register

### Packet C — rustc assumptions and downstream controls

1. Complete rustc assumption inventory.

## 9. Stop and escalation conditions

Stop and request an owner ruling if:

- the audit reveals disagreement about the language specification;
- a shared authority has no identifiable owner;
- an engine role cannot be stated without contradicting current release claims;
- rustc behavior varies materially across supported versions;
- evidence independence cannot be determined;
- a proposed fix would redesign the engine architecture;
- the work expands beyond AS0's approved assurance scope or would change project-roadmap
  scheduling.

This packet does not authorize semantic redesign.

## 10. Exit criteria

WP-ENGINE-INDEPENDENCE is complete when:

1. every known semantic authority shared by two or more engines is registered;
2. direct and indirect dependencies are distinguished;
3. shared semantic data is included, not only shared functions;
4. correlated test oracles and fixture generators are registered;
5. every shared authority has independent evidence or an explicit residual;
6. rustc assumptions and toolchain identity requirements are documented;
7. HIR, MIR interpreter, and native have explicit role and risk profiles;
8. AS8 receives ranked shared-authority mutation targets;
9. C10 receives release metadata requirements;
10. public engine language is calibrated to measured evidence;
11. machine-readable outputs validate;
12. unresolved items have owners and review triggers.

## 11. Expected outcome

The packet should make it possible to answer, with evidence:

```text
How independent are the three engines?
Which semantic facts are shared?
Where can differential testing still detect divergence?
Where is agreement a shared-fate result?
What independently checks those shared facts?
What does native execution delegate to rustc?
What can be claimed publicly?
```

The success condition is not maximum independence.

It is:

> **Every intentional loss of independence is visible, justified, and covered by an assurance instrument suited to shared-fate risk.**
